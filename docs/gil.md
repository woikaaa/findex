## Що таке GIL

GIL (Global Interpreter Lock, глобальне блокування інтерпретатора) — це замок:
в один момент байт-код Python виконує лише один потік. Потоки не виконуються
по-справжньому одночасно, вони чергуються. GIL захищає внутрішні структури самого
інтерпретатора (наприклад, лічильники посилань), але **не захищає мої власні
дані**: операція `counter += 1` складається з трьох кроків (прочитати, додати,
записати), і потік може бути перемкнений між ними.

## Чому потоки не прискорили індексацію

Індексація — це робота процесора: розбити текст на слова, нормалізувати, порахувати.
Весь час потрібен байт-код Python, а під GIL його виконує один потік. Тому 2, 4 чи 8
потоків просто стоять у черзі на один замок. У таблиці це видно: wall time з потоками
`<<порівняй: threads 1 → <<X>> с, threads 4 → <<Y>> с>>` майже не зменшується або навіть
росте (потоки ще витрачають час на перемикання). CPU time при цьому не зменшується,
бо сума роботи та сама.

## Чому процеси прискорили (або ні) і чим це оплачено

Кожен процес має **свій** інтерпретатор і **свій** GIL, тому на різних ядрах
вони справді працюють одночасно. `<<processes 4 → <<Z>> с, прискорення <<S>>×>>`.

Ціна:

- **CPU time (процесорний час) не зменшується, а росте**: сума роботи всіх процесів
  більша за serial, бо додаються запуск процесів (spawn: кожен імпортує findex з нуля)
  і pickle. Wall time (час за годинником) зменшується, а CPU time — ні.
  `<<serial CPU = A с, processes 4 CPU = B с>>`.
- **Пам'ять**: кожен процес тримає свою частину індексу, а потім вона
  пересилається батьківському через pickle (копія). Пік RSS (пам'ять, яку процес
  реально займає) у батьківського процесу вищий: `<<serial = M1 МБ, processes = M2 МБ>>`.
- **Передача даних**: у воркер їдуть лише шляхи до файлів (мало даних), а назад —
  готова частина індексу (багато даних). Якщо корпус малий, цей час може з'їсти
  весь виграш.

## Закон Амдала: де його видно

Закон Амдала: якщо частина роботи `s` лишається послідовною, то прискорення на N
ядрах не більше ніж `1 / (s + (1 − s) / N)`. У мене послідовна частина — це `merge`
(склеювання частин в один індекс, виконується в батьківському процесі) і пересилання
результатів. `<<merge = T с, це s = P % від serial, тому межа на N ядрах = L×, а реально S×>>`.
Скільки б воркерів я не додавала, цей шматок не стискається.

## Що змінилось на 3.13t (без GIL)

Я поставила збірку командою `uv python install 3.13t`, зробила для неї окреме
середовище `.venv313t` і запускаю в ньому. Перевірка, що GIL вимкнений:
`python -c "import sys; print(sys._is_gil_enabled())"` → `False`.

`<<таблиця для threads на 3.13t: workers 1/2/4 → wall ... прискорення ...>>`.
Потоки без GIL справді виконуються паралельно на різних ядрах, тому для CPU-роботи
вони починають прискорюватись, і не треба пересилати дані через pickle.
Але зникає й «випадковий захист»: код, який на звичайному Python здавався безпечним,
починає губити оновлення.

## Гонитва (race condition)

`python -m findex.race_demo` запускає 4 потоки, кожен 300 000 разів робить
`counter += 1`. Очікую 1 200 000.

| Python                           | без Lock                  | з Lock |
| -------------------------------- | ------------------------- | ------ |
| звичайний (GIL)                  | `<<втрачено: ...>>`       | 0      |
| 3.13t (`_is_gil_enabled()` False)| `<<втрачено: ...>>`       | 0      |

Виправлення: `threading.Lock` навколо читання-додавання-запису (`with lock:`),
або в моєму індексері — не ділити стан між потоками взагалі: кожен воркер будує
**свою** частину (`build_partial`), а склеює їх один `merge`. Тоді спільних даних
для запису немає і замок не потрібен.
