# Профілювання (лаба 8)

Дата гіпотез: 10.11.2026. Ці гіпотези записані й закомічені ДО вимірювань і ДО будь-яких
змін коду. Результати нижче дописані вже після вимірювань.

## Гіпотези (до вимірювань)

Я дивилась на код і думаю так.

### Сам пошук (`Searcher.search`)

1. **Цикл по записах слова в `Searcher.search` і `BM25.score`.** Для кожного запису я викликаю
   `scorer.score`, а він ще кілька разів ходить в `index.df`, `index.num_docs`,
   `index.doc_length` і рахує `math.log`. Це викликів багато, тому очікую, що тут піде
   найбільше часу, особливо для частотного слова і для запиту з трьох слів.
   Це повільний Python (виклики функцій), а не C.
2. **`Index.__getitem__`.** Якщо індекс у форматі `array` (так його читає бінарний файл),
   то на кожен запит для слова створюється список з об'єктів `Posting`. Це друге місце.
   Теж повільний Python (створення об'єктів).
3. **`heapq.nlargest` з `lambda` і створення `dict` з нулями.** Третє місце, але набагато
   менше за перші два.

### Сторінка результатів (пошук + уривки)

1. **`make_snippet` у `snippets.py`.** Для кожного з 10 результатів я читаю весь текст,
   проходжу регулярним виразом по всіх словах і для кожного слова роблю `casefold`.
   Очікую, що тут піде більшість часу (більше половини). Тут суміш: регулярний вираз
   і `casefold` це C (native), а вкладена функція `score` це Python.

### Збірка індексу (`build_index`)

1. **`tokenize`** (нормалізація, `casefold`, регулярний вираз) і **`Counter`** в
   `_PartialBuilder.add`. Очікую, що більшість часу це токенізація, і вона здебільшого
   native (регулярний вираз, `casefold`, `normalize` це C).

## Результати (після вимірювань)

Усе міряно на моєму комп'ютері (Windows, Python 3.13) на корпусі з 40 статей
(`data/wiki`, індекс `data/wiki.bin`, 56 144 слова). Інструменти: cProfile
(`profile_run.py`), py-spy (flame graph), Scalene. Запити вибирає `bench_cases.py` за
правилом з самого індексу:

| Випадок | Запит | У скількох документах |
| ------- | ----- | --------------------- |
| частотне слово | `а` | 40 |
| рідкісне слово | `阿部重雄著` | 1 |
| три слова | `та OR час OR ж` | кілька десятків |

cProfile сам сповільнює програму, тому для часу беру запуски без нього (`--plain`).

| Що міряю | З cProfile | Без cProfile |
| -------- | ---------- | ------------ |
| один пошук (без уривків) | 0,33 мс | 0,10 мс |
| одна сторінка (пошук + уривки топ-10) | 163 мс | 103,5 мс |
| збірка індексу з 40 статей | 1,03 с | 1,12 с (замір `findex`) |

Flame graph лежать у `docs/flame_search_before.svg` і `docs/flame_page_before.svg`
(відкривати в браузері). Повні таблиці cProfile: `docs/profile_*_before.txt`.

### Три найдорожчі місця

| № | Місце | Скільки часу | Python чи native |
| - | ----- | ------------ | ---------------- |
| 1 | `make_snippet` (`snippets.py`): на сторінці | близько 95% часу сторінки (46,4 с з 49,0 с). Усередині: `unicodedata.normalize` 24%, власний цикл по всіх словах тексту 40%, `casefold` 12%, `re.Match.group` 11%, вкладена `score` 7% | 52% native, 48% Python |
| 2 | Цикл по записах слова з `BM25.score` (`ranking.py`, `scoring.py`): у пошуку | близько 59% часу пошуку (0,171 с з 0,288 с); сюди входять `Index.df` (20%), `num_docs`, `doc_length`, `math.log`. Поруч `Index.__getitem__` (створення об'єктів `Posting`) 18% і `heapq.nlargest` 8% | 82% Python, 18% native |
| 3 | `tokenize` і цикл `add` (`tokenize.py`, `index.py`): у збірці | `tokenize` близько 44% (з них `normalize` 15%), власний цикл `add` близько 35% | 60% Python, 40% native |

Python і native я рахувала по cProfile скриптом `prof_split.py`: вбудовані функції C
(`re`, `casefold`, `normalize`, `math.log`, `dict.get`) це native, решта це Python.
Для `make_snippet` частка native трохи занижена: час, який регулярний вираз витрачає
всередині циклу `for m in finditer(...)`, cProfile записує на сам `make_snippet`.
Scalene на Windows показав те саме для сторінки: у `make_snippet` майже весь час
native (5,2% native проти 0,1% Python). Але у звіті Scalene був ще рядок власного
допоміжного потоку (`threading.py: Thread.run`), тому відсотки по інших функціях
в нього занижені, і я спираюся на cProfile.

### Що з гіпотез підтвердилося

| Гіпотеза | Результат |
| -------- | --------- |
| пошук: цикл з `BM25.score` найдорожчий | підтвердилася (59%) |
| пошук: друге місце `Index.__getitem__` | підтвердилася (18%) |
| пошук: третє місце `nlargest` | підтвердилася, але це лише 8% |
| сторінка: найдорожчий `make_snippet` | підтвердилася (95%) |
| сторінка: частина `make_snippet` це Python, частина C | підтвердилася, але я не очікувала, що найбільша окрема стаття це `unicodedata.normalize` (24%): він щоразу нормалізує весь текст статті |
| збірка: найдорожча токенізація, переважно native | частково: `tokenize` 44%, але Python там більше (60%), ніж я думала, бо дорогий власний цикл `add` |

### Що з цього випливає

- Один пошук без уривків коштує 0,10 мс, а сторінка 103,5 мс. Тобто на сайті пошук у
  1000 разів швидший за уривки, і найбільше виграє той, хто прискорить `make_snippet`.
- Для самого пошуку (лабораторне завдання) ціль це цикл по записах: замість виклику
  `score` на кожен запис рахувати бали всім записам слова одним виразом NumPy.
