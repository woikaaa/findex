# Лаба 1 — потоки, а не списки: ітератори і генератори

**Що зроблено:** `iter_documents()` читає документи по одному, `tokenize()` ліниво
ріже текст на токени, `stats.py` збирає статистику корпусу за один прохід і вимірює
час та пікову пам'ять. Для порівняння написана навмисно «жадібна» версія на списках.

## Команди

```bash
python -m findex.stats data/                 # потокова (lazy) версія
python -m findex.stats data/ --limit 5       # тільки перші 5 документів (itertools.islice)
python -m findex.stats data/ --eager         # жадібна версія зі списками
```

Виводиться: кількість документів, токенів, розмір словника, топ-50 термів,
час виконання і пікова пам'ять (`tracemalloc`).

## Правила токенізатора

- **NFC-нормалізація** (`unicodedata.normalize("NFC", text)`). Один і той самий
  видимий символ можна закодувати по-різному, наприклад `é` як один символ або як
  `e` з комбінованим акцентом. Після NFC це один і той самий токен.
- **Знак наголосу (U+0301) видаляється.** У Вікіпедії наголоси позначені окремим
  комбінованим символом (`Архітекту́ра`). Для кирилиці NFC його не склеює з літерою,
  а `\w` не вважає його частиною слова, тож без цього слово розпадалося на два токени
  (`архітекту` і `ра`). Тепер це один токен `архітектура`. Цю помилку я знайшла, коли
  в результатах пошуку побачила слова з наголосами, і додала для неї окремий тест.
- **`casefold()`, а не `lower()`.** `casefold` призначений для порівняння без
  урахування регістру: `"Straße".casefold() == "strasse"`, а `lower()` цього не зробить.
- **`re.finditer`, а не `re.findall`.** `finditer` віддає збіги по одному, а `findall`
  будує список усіх збігів.
- **Апострофи** (`'` і `’`) лишаються всередині слова (`don't`, `п'ять`), а на краях
  відкидаються (`'hello'` дає `hello`).
- **Дефіси** лишаються всередині слова (`well-known`) і відкидаються на краях.
- **Цифри** входять у `\w`, тому число стає окремим токеном (`2024`).
- `\w` у Python 3 працює з Unicode, тож кирилиця й латиниця з акцентами розпізнаються
  без додаткових прапорців.

## Вимірювання: eager проти lazy

| Версія            | Документів | Токенів | Пікова пам'ять | Час      |
| ----------------- | ---------- | ------- | -------------- | -------- |
| eager (списки)    | 40         | 268 667 | 29363.1 KiB    | 0.9579 s |
| lazy (генератори) | 40         | 268 667 | 9075.3 KiB     | 1.0713 s |

Обидві версії дають однаковий результат (той самий словник із 56 144 слів і ті самі
лічильники). Жадібна версія використала приблизно **у 3,2 раза більше** пам'яті
(29363,1 проти 9075,3 KiB). За часом різниці немає: у цьому запуску жадібна версія
навіть вийшла трохи швидшою, але це в межах похибки вимірювання, тож генератори
економлять саме пам'ять, а не час.

**Куди пішла пам'ять.** Жадібна версія одночасно тримає в пам'яті: список усіх
документів (кожен із повним текстом), список списків токенів по документах, один
плоский список усіх 268 667 токенів і лише потім будує `Counter`. Потокова версія в
будь-який момент тримає один документ, кілька токенів «в польоті» і `Counter`.

Різниця «лише» у 3,2 раза, а не набагато більша, бо `Counter` займає кілька
мегабайтів в обох версіях: у корпусі 56 144 різні слова (українська мова з
закінченнями дає багато форм слова), а `Counter` — це і є результат, його ніде
не позбутися. Тому пам'ять lazy-версії не дорівнює нулю.

У топі слів видно службові слова з виносок Вікіпедії (`wayback`, `machine`,
`архівовано`) та одно-літерні скорочення (`с`, `м`, `о`). Це не помилка
токенізатора: у статтях є посилання виду «Архівовано з оригіналу… Wayback Machine»
і скорочення «с.» (сторінка), «м.» (місто). Фільтрація таких слів не входила в цю лабу.

# Лаба 2 — інвертований індекс

**Що зроблено:** індекс «термін → відсортований список постінгів (doc_id, частота)»,
що будується за один прохід ліниво поточеним корпусом. `Posting` і `DocMeta` — це
`@dataclass(frozen=True, slots=True)`. Булевий пошук (AND, OR, NOT) реалізований
двома способами: злиття двох відсортованих списків двома вказівниками і через `set`.
Індекс зберігається у двох форматах. Порівняно три способи зберігати постінги.

Запит читається зліва направо: `a b` означає AND, є `OR` і `NOT` (це AND NOT).
Оператори пишуться **великими** літерами, щоб звичайне слово «or» теж можна було шукати.

## Команди

```bash
python -m findex.index data/ --out index.bin                     # побудувати й зберегти (pickle)
python -m findex.index data/ --out index.fbin --format binary    # власний бінарний формат
python -m findex.index data/ --out index.bin --positions         # зберегти ще й позиції токенів
python -m findex.search index.bin "київ"
python -m findex.search index.bin "київ OR львів" --engine set
python -m findex.bench index.fbin                                # merge проти set
python -m findex.memstudy data/                                  # таблиця пам'яті
```

Індекс у цьому корпусі: **56 144 терміни, 119 964 постінги**, тобто в середньому
**2,14 постінга на термін**.

## Три способи зберігання постінгів

| Представлення постінгів              | Пікова пам'ять (побудова) | Пам'ять індексу | Розмір pickle | Час завантаження |
| ------------------------------------ | ------------------------- | --------------- | ------------- | ---------------- |
| `list[Posting]`, звичайний dataclass | 25.9 MB                   | 22.9 MB         | 3.83 MB       | 0.166 s          |
| `list[Posting]`, `slots=True`        | 21.0 MB                   | 18.1 MB         | 3.11 MB       | 0.624 s          |
| пари `array('I')`, без об'єктів      | 23.3 MB                   | 20.4 MB         | 3.99 MB       | 0.194 s          |

**Куди пішли байти.**

- Звичайний dataclass: кожен постінг — це окремий об'єкт із власним `__dict__`,
  найбільше пам'яті.
- `slots=True`: `__dict__` зникає, залишається об'єкт фіксованого розміру, тому
  це найекономніший варіант на моєму корпусі (21.0 MB проти 25.9 MB).
- `array('I')`: doc_id і частота зберігаються як «голі» 4-байтові числа. Я очікувала,
  що це буде найкращий варіант, але він вийшов посередині. Причина в тому, що слів у
  корпусі багато (56 144), а постінгів на слово мало (в середньому 2,14). Для кожного
  слова `array` створює кортеж і два окремі масиви, і ці фіксовані накладні витрати
  перевищують економію на самих числах. `array` виграє тоді, коли в слів довгі списки
  постінгів. Це пояснення випливає з виміряного середнього 2,14 постінга на слово;
  окремо накладні витрати одного масиву я не вимірювала.

Час завантаження pickle від запуску до запуску помітно коливається (наприклад, для
`slots` я отримала від 0.278 до 0.624 s), тому порівнювати його варто лише за порядком
величини. У всіх моїх запусках варіант зі `slots` завантажувався найповільніше: при
розпакуванні frozen+slots dataclass кожен об'єкт відновлюється через
`object.__setattr__`, а це повільно. Отже, `slots` виграє в пам'яті, але програє в
часі завантаження з pickle.

## Позиції токенів (`--positions`): ціна

| Зберігання          | Пікова пам'ять без позицій | З позиціями     | Розмір pickle (без / з) |
| ------------------- | -------------------------- | --------------- | ----------------------- |
| звичайний dataclass | 25.9 MB                    | 41.2 MB (+59 %) | 3.83 / 4.75 MB          |
| slots               | 21.0 MB                    | 36.4 MB (+73 %) | 3.11 / 4.03 MB          |

Побудова індексу з позиціями теж повільніша: 4.38 s проти 2.66 s (slots). З позиціями
зберігається кожне окреме входження слова (всього 268 667), тоді як постінгів лише
119 964. Формат на `array` позицій не підтримує.

## Збереження і завантаження: два формати

| Формат                                          | Розмір файлу | Час збереження | Час завантаження |
| ----------------------------------------------- | ------------ | -------------- | ---------------- |
| pickle (постінги зі `slots`)                    | 3 106 461 B  | 0.618 s        | 1.474 s          |
| власний бінарний (JSON-заголовок + `array('I')`) | 2 828 458 B  | 0.063 s        | 0.812 s          |

Час завантаження тут виміряний усередині `findex.search` під `tracemalloc`, який
сповільнює Python, тому абсолютні значення завищені. Порівнювати варто формати між
собою: бінарний швидший приблизно в 1,8 раза при збереженні й завантаженні, а
збереження швидше майже в 10 разів.

## Булевий AND: merge проти set

Два найчастіші терміни: `а` (df 40) і `або` (df 40), тобто вони є в усіх документах.
Два найрідші: `茶` і `阿部重雄著` (df 1, ієрогліфи з однієї статті).

| Випадок                 | merge  | set    |
| ----------------------- | ------ | ------ |
| частий AND частий       | 5.5 µs | 3.5 µs |
| рідкісний AND рідкісний | 0.3 µs | 0.5 µs |
| частий AND рідкісний    | 3.7 µs | 1.4 µs |

**Висновок.** Обидва способи мають складність O(n+m). Найдовший список тут має
лише 40 документів, тому все вимірюється мікросекундами. На частих термінах `set`
швидший, бо `set(a) & set(b)` виконується на C, а моє злиття — це цикл на Python.
Merge трохи швидший лише коли обидва списки складаються з одного елемента (немає
витрат на створення множин). Справжня користь merge не в швидкості в CPython: він
працює потоково, не потребує додаткової пам'яті, працює з відсортованими списками й
використовується для фразових запитів у лабі 3.

## Безпека

`pickle.load` може виконати довільний код із файлу, тому **ніколи не завантажуй
pickle, якого не створила сама**. Власний бінарний формат лише розбирає JSON і
копіює байти, тож він безпечний.

# Лаба 3 — ранжування і модель об'єктів

**Що зроблено:** `Index` став об'єктом, який поводиться як словник (клас
`collections.abc.Mapping`). Булевий пошук перетворився на ранжований список
(TF-IDF і BM25). З'явилася мова запитів із дужками й фразами, декоратор `@timed`,
кеш `lru_cache` і сніпети з підсвіченими словами.

Мова запитів: `a b` (AND), `AND`, `OR`, `NOT`, дужки, `"точна фраза"`. Оператори
пишуться великими літерами. AND зв'язує сильніше за OR, тому `a OR b c` — це
`Or(a, And(b, c))`. Для фразових запитів індекс має бути побудований з `--positions`.

`Index` підтримує `len(index)`, `"term" in index`, `index["term"]`, `for t in index`,
`repr(index)`, а також `num_docs`, `avg_doc_length` (`cached_property`) і `df`.
Функція `store.open_index(path)` — це `@contextmanager`, який викликає `index.close()`
у блоці `finally`, навіть якщо всередині `with` виникло виключення.

## Команди

```bash
python -m findex.index data/ --out index.bin --positions          # позиції потрібні для фраз
python -m findex.ranking index.bin "київ OR львів" -k 5           # ранжований пошук зі сніпетами
python -m findex.ranking index.bin '"київська русь"' -v --repeat 2 # лог @timed і кешу
python -m findex.ranking index.bin "алгоритм AND (дані OR структура)" --scorer tfidf
python -m findex.sanity index.bin                                 # три перевірки ранжування
python -m findex.evaluate index.bin queries.json                  # precision@5
```

## Три перевірки ранжування (`python -m findex.sanity`)

BM25 з k1=1.5, b=0.75; 40 документів, середня довжина документа 6716.7 токена.

1. **Рідкісний термін оцінюється вище за частий** (один документ, tf=1): `0-0`
   (df=1) отримує **3.478**, а `її` (df=40) лише **0.013**.
2. **Насичення частоти** (документ середньої довжини, терм `0-0`): tf=1 → 3.478,
   tf=2 → 4.897, tf=10 → 7.269, tf=20 → 7.737, tf=21 → 7.761. Друге входження
   додає **1.419**, а 21-ше лише **0.0238**.
3. **Нормалізація довжини** (одне входження): короткий документ (439 токенів)
   отримує **5.709**, довгий (25 403 токени) лише **1.469**.

## Логи `@timed` і кешу (`-v --repeat 2`)

```
[findex.timing] load took 349.49 ms
[findex.timing] Searcher.search took 0.34 ms
[findex.search] cache hit for 'київ OR львів'
[findex.timing] Searcher.search took 0.41 ms
```

`lru_cache` загортає крок «запит → id знайдених документів». Кеш створюється окремо
для кожного `Searcher`, бо `Index` не є хешованим (це `Mapping`), а `lru_cache`
потребує хешованих аргументів.

Другий виклик **не став швидшим** (0.41 проти 0.34 ms): кеш запам'ятовує лише
крок знаходження документів, а підрахунок балів виконується щоразу, і на малому
корпусі різницю перекриває шум вимірювання. Те, що кеш спрацював, видно з рядка
`cache hit`.

## Чому «Київ» не на першому місці для запиту «київ OR львів»

Для цього запиту BM25 ставить на перші місця «Карпати» (2.089), «Архітектуру»
(2.026) і «Футбол» (1.997), а статті «Київ» у топ-3 немає. Це не збій, а наслідок
формули:

- Слово «київ» є майже в усіх статтях (29 зі 40), тому його вага IDF мала
  (приблизно 0,33).
- Через насичення частоти внесок одного слова обмежений зверху величиною
  приблизно IDF × (k1 + 1), тобто близько 0,82. Стаття «Київ» з 121 повтором слова
  набрала близько 0,8, тобто майже вичерпала цей максимум; решта повторів нічого не
  додають.
- У запиті з OR короткі статті, які згадують і Київ, і Львів по одному разу, додають
  бали обох слів.

## precision@5: TF-IDF проти BM25 (`python -m findex.evaluate`)

10 запитів із розміткою (`queries.json`). Запити з кількох слів виконуються як OR.
P@5 = (кількість релевантних документів у топ-5) / 5, тому запит, для якого
релевантний лише 1 документ, може отримати щонайбільше 0.20.

| Запит                          | релевантних | P@5 TF-IDF | P@5 BM25 |
| ------------------------------ | ----------- | ---------- | -------- |
| поет вірші збірка              | 4           | 0.80       | 0.80     |
| алгоритм структура дані        | 3           | 0.40       | 0.40     |
| нейронна мережа навчання       | 2           | 0.40       | 0.40     |
| планета зірка Сонце            | 2           | 0.40       | 0.40     |
| шахова партія фігури           | 1           | 0.20       | 0.20     |
| кавові зерна напій             | 2           | 0.40       | 0.40     |
| козаки гетьман Січ             | 3           | 0.40       | 0.40     |
| футбольний клуб чемпіонат      | 2           | 0.20       | 0.20     |
| операційна система ядро процес | 3           | 0.20       | 0.20     |
| пошукова система індекс        | 3           | 0.20       | 0.20     |
| **середнє**                    |             | **0.36**   | **0.36** |

**Висновки.**

- Обидва скорери показали однакове середнє P@5 (0.36). На корпусі з 40 статей, де
  для кожного запиту є кілька очевидних відповідей, ця різниця не проявляється.
- Для запитів, де «правильна» відповідь одна (наприклад, «шахова партія фігури»),
  максимум P@5 дорівнює 0.20, і обидва скорери його досягають: потрібна стаття в
  топ-5. Нижчі значення в інших рядках пояснюються тим, що серед топ-5 потрапляють
  сторонні статті.
- Через OR у запит потрапляють загальні слова, які є в багатьох статтях. Наприклад,
  для запиту «операційна система ядро процес» у топі разом із потрібною статтею
  опинилась «Сонячна система», імовірно через слово «система».
- Пошук працює з точними формами слів без лематизації: «козаки» не знайде «козак».
  Через це довелося добирати слова, що трапляються в статтях саме в такому вигляді.
